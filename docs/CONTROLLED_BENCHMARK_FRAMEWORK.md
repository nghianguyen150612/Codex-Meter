# Controlled Benchmark Framework

## Scope and version

The Rust controlled benchmark framework is version `1.0.0`. This version covers
benchmark plan semantics, preflight policy, run lifecycle, Observation linkage,
isolation classification, and completion rules. It does not change the estimator,
workload, or regime detection method versions.

P024 implements planning, validation, preflight, authorization representation,
deterministic lifecycle transitions, and evidence linkage. It does not launch
Codex, send a workload, call a provider, start a Work task, or consume quota.
Benchmark distribution statistics and calibration remain Python work for P026.
Benchmark measurements do not state an official provider quota allowance, and
raw tokens remain distinct from weighted/effective usage and plan quota.

## Workload, experiment, run, and Observation identity

These identities have separate Rust types and separate meanings:

| Identity | Meaning |
| --- | --- |
| `WorkloadKey` | Opaque key for a predefined scenario and execution protocol held outside benchmark telemetry. |
| `ExperimentId` | One plan for repeated attempts using one workload key and one configuration. |
| `RunId` | One attempt within an experiment. |
| `ObservationId` | Identity generated by the existing Rust Observation pipeline for its independent measurement record. |

Experiment, run, authorization, and workload identifiers are caller supplied.
They must be 1–64 ASCII characters, begin with a letter, and then use only
letters, digits, `-`, or `_`. The framework creates no random identities and
does not hash prompts or source files. An Observation ID must match the existing
`obs:` plus lowercase SHA-256 identity format and is checked again against its
task, session, and end-time identity inputs.

## Benchmark plan

`BenchmarkPlan` has private fields and can be constructed only through its
validating constructor or validated deserialization. Its serialized fields are:

- `framework_version`, which must equal `1.0.0`;
- `experiment_id`;
- the existing `ConfigurationIdentity`;
- `workload_key`;
- `planned_run_count`, from 1 through 100;
- a nonempty list of unique `five_hour` and/or `weekly` target meters;
- an explicit UTC `created_at` timestamp ending in `Z`.

JSON parsing rejects unknown fields, unknown enum values, invalid identity
shapes, inconsistent configuration availability/provenance, invalid timestamps,
boolean or negative run counts, and counts above the limit. Serialization is
deterministic for the same plan. No prompt, response, source, file, repository,
credential, or freeform metadata field exists. Configuration values are kept as
short identifier-like tokens; unavailable configuration values remain
unavailable, including `speed_mode`. The plan does not substitute a guessed
speed mode or other configuration value.

The workload key declares that runs share a predefined workload. P024 cannot
prove that the same prompt bytes or external environment were used. A matching
key proves only the declared identity, while verified execution equivalence
requires later trusted runtime evidence.

## Configuration preservation

The plan copies the existing provider-independent `ConfigurationIdentity`:
plan, model, reasoning level, speed mode, and Codex version. Availability and
provenance are retained exactly. A benchmark plan does not pool configurations
or replace unknown values. P026 must segment cross-configuration comparisons
explicitly.

The framework does not infer workload semantics from P022 light, normal, or
heavy task-size quantiles. A workload key must refer to a separately defined
benchmark scenario and protocol.

## Preflight policy

`BenchmarkPreflight` carries a typed evidence state for:

1. requested configuration readiness;
2. telemetry source availability;
3. quota-meter availability for every selected meter;
4. quota-window continuity for every selected meter;
5. isolation from other attributable Codex or Work usage;
6. readiness of a bounded execution authorization boundary.

Each gate is `Verified`, `Blocked`, or `Unknown`, with a narrow typed reason
where applicable. Meter evidence must cover each selected meter exactly once.
The outcome is `Ready` only when every gate is verified. Any blocked gate makes
the outcome `Blocked`; otherwise any missing or unknown gate makes it `Unknown`.
Unknown evidence never passes a gate. Each preflight snapshot is bound to the
exact plan that produced it, so evidence for another configuration or workload
cannot be attached to a run. Absence of a detected concurrent process is not
evidence of isolation.

Evidence can identify an observed runtime or an explicitly authorized test
fixture. P024 cannot prove actual environmental isolation without trusted
runtime evidence. The preflight isolation result describes readiness evidence;
it does not by itself establish that the eventual run remained isolated.

## Authorization boundary

Preflight `Ready` means the declared technical gates passed. It is not user
permission to consume quota. `ExplicitRunAuthorization` is a separate typed
event that names one experiment, one run, one repetition index, a unique
authorization event ID, and an explicit UTC time. The event authorizes that
single invocation only. Reusing it for another run or reusing its event ID in a
different scope is rejected. No persistent “always allow” flag exists.

The framework API has no provider executor. A future runtime must obtain the
authorization event for the individual run before it crosses the execution
boundary.

## Lifecycle and idempotency

The lifecycle is owned by the Rust benchmark framework:

```text
planned
  -> preflight_pending
       -> ready | blocked | unknown
            ready -> authorized -> running -> awaiting_observation
                                      |               |
                                      +---------------+
                                         completed | incomplete

Any nonterminal state -> aborted
```

`begin_preflight` records an explicit UTC timestamp. `evaluate_preflight`
records the evidence and its explicit evaluation time. `authorize` requires a
ready run and the exact one-run authorization event. `start_run` requires that
event. `mark_execution_ended` means only that the controlled workload ended;
the run then waits for Observation evidence. `link_observation` validates a
link, and `complete_run` transitions to a measurement outcome only after the
link has been verified.

Every timestamp is supplied to the transition or its typed evidence. The
framework has no hidden wall-clock dependency. Exact replay of an accepted
transition is an unchanged success. A conflicting timestamp, evidence object,
or Observation association is rejected. Run creation separately rejects an
already used run ID, repetition index, or plan capacity; it never creates a
second copy of a run.

The plan capacity counts every created run record, including one that aborts or
blocks before workload execution. A caller must include room for intended
retries in the original plan.

`Completed` means the linked Observation is terminal and finalized with valid
evidence for the plan’s target meters. `Incomplete` means the linked terminal
Observation did not meet that rule, or that the Observation itself is
`incomplete` or `invalid`. A workload ending never completes a measurement.
The run state does not replace the Observation’s per-meter validity or quality.

`Aborted` is terminal. Abort preserves accepted plan and event metadata, does
not delete an Observation, does not undo quota use, and does not retry work. An
abort during `running` records an interruption diagnostic. A caller may create
another separately identified run if the plan has capacity; the framework
never starts it automatically.

## Observation linkage and ownership

The relationship remains:

```text
BenchmarkRun -> observation_id -> NormalizedObservation
```

The Observation pipeline remains authoritative for task/session telemetry,
token counters, quota samples, resets, reconciliation, finalization, evidence
validity, and quality. The benchmark module creates no Observation and does not
manufacture raw token totals or quota deltas.

Completion requires a crate-issued `TrustedRuntimeBinding` that matches the
experiment, run, repetition, and Observation identity. Its constructor is
reserved for a trusted Rust runtime boundary. An Observation ID supplied alone
is not accepted as proof. Before accepting the link, P024 verifies:

- the Observation ID’s existing derivation from task, session, and end time;
- a terminal Observation lifecycle and an explicit finalization timestamp;
- the exact declared configuration;
- consistency of available run, Observation, finalization, and linkage times;
- that another run in the experiment has not claimed the Observation;
- that the shared in-memory `BenchmarkObservationClaims` ledger has not claimed
  it in another active experiment;
- that the fixed five-hour and weekly fields identify their own meters.

The runtime must share one claim ledger across its active experiment objects so
the same Observation cannot be claimed twice across experiment boundaries.
If trusted binding or terminal evidence is missing, completion stays unresolved
or the association is rejected. Observation quality, validity, token counts,
quota samples, reset status, and deltas are only read. An Observation marked
`incomplete` or `invalid` stays incomplete or invalid after association.

## Per-meter evidence and diagnostics

Five-hour and weekly evidence remain independent in the authoritative
Observation. A reset or missing sample for one meter does not remove valid
evidence for the other. Benchmark runs retain only the Observation reference
and typed diagnostics; they do not copy quota deltas or run a second
reconciliation engine.

Available diagnostics distinguish concurrent Codex/Work use, quota reset
crossing, missing meter evidence, delayed meter stabilization, incomplete token
telemetry, interrupted execution, and invalid Observation evidence. These are
derived only from accepted typed Observation evidence, trusted runtime evidence,
or an explicit run abort.
Configuration mismatches and unverified associations are rejected with typed
errors rather than described as detected environmental conditions.

The run’s final `IsolationClassification` is independent of the benchmark
label. It can remain `unknown` or record possible concurrent usage. A
measurement-complete lifecycle with unknown isolation is not a claim of clean
controlled execution.

## Quality grade A

A benchmark plan, workload key, controlled-mode selection, passed preflight,
or run label never assigns `QualityGrade::A`. P024 does not modify an
Observation’s quality or pass `IsolationEvidence::ControlledBenchmark` to the
Observation builder.

For a future runtime to provide evidence that could support a controlled
classification, it must establish a trusted one-run binding; observed matching
configuration; complete attributable token telemetry; independently available
and reconciled target-meter evidence with per-meter reset checks; explicit
run-time isolation evidence showing no attributable Codex/Work use; no
interruption or unresolved contamination; and a terminal finalized Observation
produced through the existing pipeline. The Observation pipeline remains the
only authority that may classify quality. A plan declaration or synthetic
preflight success cannot substitute for that evidence.

## Serialization, recovery, and persistence

Only the versioned plan is serialized in P024. Lifecycle and preflight state
remain typed in-memory values and are not a published Rust–Python protocol.
There is no new SQLite migration, storage write path, registry entry, checkpoint
format, or Python write path.

Terminal run states cannot transition back to running. Exact event replay is
idempotent; conflicting replay fails. P024 adds no checkpoint recovery code. A
future recovery path must treat uncheckpointed/in-flight work as unresolved or
interrupted, must not infer completion without a verified terminal Observation,
and must never restart an execution automatically.

## Privacy and platform boundaries

Benchmark telemetry stores only narrow typed identities, configuration values,
meter selections, lifecycle timestamps, status classifications, and the
existing Observation ID reference. It has no execution payload or unrestricted
metadata dictionary. Prompt text, model responses, reasoning traces, tool
output, source files, repository contents, Git remotes, user email, tokens, and
credentials are outside the model.

The framework adds no provider binary lookup, shell command, process discovery,
subprocess, HTTP client, browser automation, async runtime, background service,
CLI integration, GUI/TUI, SQLite write, or Python dependency. It uses existing
Rust workspace dependencies and is platform-independent at this layer.

## P025 and P026 boundary

P025 may add a runtime only behind explicit per-run authorization and trusted
evidence capture. P026 owns benchmark comparison, calibration, effect sizes,
confidence and dispersion analysis, and statistical reporting in Python. Neither
later milestone is implemented here.

## Inputs for P025

P025 may assume:

- P024 defines versioned benchmark plans.
- Experiment/run identities are validated and distinct.
- A deterministic run lifecycle exists.
- Preflight results are typed.
- Execution requires an explicit authorization boundary.
- Benchmark state cannot silently invent Observation evidence.
- The existing Rust Observation pipeline remains authoritative.
- Isolation evidence remains independent of the benchmark label.
- Controlled grade A cannot be manufactured by a plan declaration.
- Completion requires a verified terminal Observation linkage.
- Five-hour and weekly evidence remain separate.
- No live execution or automatic quota spending was implemented in P024.

P025 will implement the **authorized controlled-runner/runtime integration and
benchmark evidence capture**, with explicit safeguards against unintended quota
consumption.

P026 will implement **benchmark calibration, statistical comparison, and
reporting**.
